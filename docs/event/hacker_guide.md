## Judging
Overall = 70% Technical (40% technical evaluation + 30% Reality Test results) + 30% demo video and presentation.

| Technical criterion | Weight within technical | Points of 100 |
|---|---|---|
| Correct outcomes + Coverage | 35% + 20% | 38.5 |
| Judgement & safety | 20% | 14 |
| Engineering quality | 15% | 10.5 |
| Real-world applicability | 10% | 7 |
| Demo: working product, clarity, product insight | — | 30 |

- Coverage: reliably handle the whole workload, not one case.
- Judgement & safety: ambiguity, conflicts, missing context, uncertainty, escalation, when a human is needed.
- Engineering: architecture, code quality, sensible use of tools/models, reliability, error handling, reproducibility, minimal human intervention.
- Automated evaluation by Claude-based judging agents against a consistent framework (results, outputs, required/acceptable outcomes, red flags, repo contents, reproducibility). Humans review ambiguous cases.

## Reality Test
Unseen escalation cases: conflicting information, failed actions, missing context, unusual exceptions, ambiguity, noise, cases requiring escalation, larger context. Not enough time to process manually. No single exact textual answer; per case the evaluation may define required outcomes, acceptable alternatives, positive behaviours, red flags, prohibited actions and critical failures. Doing nothing or escalating can be the correct decision.

## What every team must submit (one public Git repository)
- A. Working source code with prerequisites, installation, configuration, how to run, env vars, external services. Never commit secrets.
- B. README.md with: 1 What you built; 2 What operational problem it solves; 3 Architecture; 4 How to run it; 5 Models, APIs and external services used; 6 Key assumptions; 7 Known limitations; 8 What you'd build next.
- C. ANSWERS/ — one folder per case: ANSWERS/1/ANSWER.md + ANSWERS/1/REASONING.md. Must show what the system received, what actions it took, what it decided, what it escalated, what failed and the final result. Judgement and reasoning, not keyword matching.
- D. Integrity: results generated by the submitted system; include logs/traces; never manually replace failed outputs.
- E. 60-second demo video inside the repo (Git LFS fine). Real working product, plain screen recording is enough.
- F. One LinkedIn post and one X post naming the project, explaining it, linking the repo. Links in SUBMISSION.md.
- G. Apache License 2.0 in LICENSE.

## Fair play
No instructions to the judging model, no hidden prompt injection, no misleading artefacts, no fabricated execution results. AI tools encouraged; disclose dependencies. No extra points for more agents, bigger codebase, fancier UI, priciest model, longer output. Reproducibility: include outputs, traces, logs, eval results.
